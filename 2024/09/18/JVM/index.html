JVM的生命周期

虚拟机的启动

Java虚拟机的启动是通过引导类加载器(bootstrap class loader)创建一个初始类(initial class)来完成的，这个类由虚拟机具体的实现指定

虚拟机的执行

程序开始执行它才运行，程序结束它就停止。

虚拟机的退出

  • 程序正常执行结束
  • 异常或错误导致异常终止
  • 操作系统错误，导致Java虚拟机进程终止
  • 调用Runtime或System类的exit等操作

类加载器子系统

  • class文件开头需要有特定的文件标识
  • ClassLoader只负责class文件加载，能否运行由Execution Engine决定
  • 加载的类信息存放在叫方法区的内存空间，方法区中还存放运行时常量池信息

类的加载过程

Loading->Verification->Preparation->Resolution->Initialization

​ Linking

Loading

  • 通过一个类的全限定名获取二进制字节流
  • 将字节流代表的静态存储结构转化为方法区的运行时数据结构
  • 在内存中生成一个代表这个类的java.lang.Class对象，作为方法区这个类的各种数据的访问入口

Linking

Verification

使class文件的字节流中包含信息符合当前虚拟机要求，保证被加载类的正确性，不会危害虚拟机自身安全

Preparation

为类变量分配内存并且设置默认初始值，零值

如果用final修饰的static，因为在编译阶段就会分配，那么准备阶段就会显式初始化。

这里不会为实例变量分配初始化

Initialization

初始化阶段就是执行类构造器方法()的过程

此方法不需要定义，自动收集类中的类变量赋值动作和静态代码块中的语句合并而来

构造器方法中指令按照源文件中出现的顺序执行

虚拟机必须保证类的()方法在多线程下被同步加锁

几种类加载器

JVM支持两种类型的类加载器，分为引导类加载器(Bootstrap ClassLoader)和自定义类加载器

Bootstrap ClassLoader：

  • 使用c/c++语言实现的，嵌套在JVM内部
  • 加载Java的核心库JAVA_HOME/jre/lib/rt.jar、resources.jar或sun.boot.class.path路径下的内容
  • 并不继承ClassLoader类，没有父加载器
  • 它加载了扩展类加载器和应用程序类加载器

JVM定义自定义类加载器是所有派生于抽象类ClassLoader的类加载器都划分为自定义类加载器

对于用户自定义类来说，默认使用系统类加载器(System ClassLoader)

获取类加载器的途径（随便了解一下）

  • 获取当前类的ClassLoader:class.getClassLoader()
  • 获取当前线程上下文的ClassLoader:Thread.currentThread().getContextClassLoader()
  • 获取系统的ClassLoader:ClassLoader.getSystemClassLoader()
  • 获取调用者的ClassLoader:DriverManager.getCallerClassLoader()

用户自定义加载器

为什么要自定义

  • 隔离加载类(由于中间件都有自己依赖的jar包，如果引入多个框架，遇见某些类路径一样类名相同，避免类的冲突)
  • 修改类加载的方式
  • 扩展加载源
  • 防止源码泄漏

自定义实现步骤

  • 继承抽象类java.lang.ClassLoader类
  • JDK1.2后，建议直接把自定义类加载逻辑写在findClass()方法中
  • 如果没有复杂的需求，可以直接继承URLClassLoader类，避免编写findClass()方法以及其获取字节码流的方式

双亲委派机制(重要)

JVM对class文件采用按需加载，需要使用时才加载到内存中。加载某个类的class文件时，采用双亲委派机制，即把请求交由父类处理

  • 类加载器收到了加载请求，并不会自己去加载，而是把这个请求委托给父类的加载器去执行
  • 如果父类加载器还存在其父类加载器，则进一步向上委托，依次递归，请求最终将到达顶层的启动类加载器
  • 如果父类加载器可以完成类加载，就成功返回，倘若父类加载器无法完成此加载任务，子加载器才会尝试自己去加载

优势

  • 避免类的重复加载
  • 保护程序安全，避免核心API被随意篡改

沙箱安全机制

自定义String类中写了main方法，但是加载类的时候会使用引导类加载器加载，加载JDK自带的文件，因此会报错说没有main方法。这样可以保证对源代码的保护。

运行时数据区

红色的是一个进程一份，灰色的是一个线程一份

PC寄存器

JVM中的PC寄存器是对物理PC寄存器的一种抽象模拟，用来存储指向下一条指令的地址，也即将要执行的指令代码。由执行引擎读取下一条指令

PC寄存器既没有垃圾回收，也不会溢出

虚拟机栈

栈是运行时的单位，而堆是存储的单位。

栈不存在垃圾回收问题，但是会溢出

Java栈的大小是动态的或者是固定不变的

  • 如果采用固定大小的虚拟机栈，那每一个线程的虚拟机栈容量可以在线程创建的时候独立选定。如果线程请求分配的栈容量超过Java虚拟机栈允许的最大容量，Java虚拟机将会抛出一个StackOverflowError异常

  • 如果虚拟机栈可以动态扩展，并且在尝试扩展的时候无法申请到足够的内存，或者在创建新的线程时没有足够的内存去创建对应的虚拟机栈，那么会抛出一个OutOfMemoryError异常

  • 栈中的数据都是以栈帧的格式存在

  • 在这个线程上正在执行的每个方法都各自对应一个栈帧

  • 栈帧是一个内存区块，是一个数据集，维系着方法执行过程中的各种数据信息

当前栈帧-当前方法，定义这个方法的类就是当前类

return和抛出异常，都会导致栈帧被弹出

栈顶缓存技术：

将栈顶元素全部缓存在物理CPU的寄存器中，以此降低对内存的读/写次数，提升执行引擎的执行效率

栈帧：

  • 局部变量表
    • 定义为一个数字数组，主要存储方法参数和定义在方法体内的局部变量
    • 线程的私有数据，不存在数据安全问题
    • 所需的容量大小是在编译器确定下来的
    • 最基本的存储单元Slot(变量槽)
    • 34位以内的类型只占用一个Slot，64位的类型(long和double)占用2个Slot
    • JVM为每一个Slot都分配一个访问索引，通过索引访问到局部变量值
    • 如果当前帧是由构造方法或者实例方法创建的，那么该对象引用this将会存放在索引为0的slot处
    • 局部变量表中的槽位可以重用，从而节省资源
    • 局部变量表中的变量也是重要的垃圾回收根节点，只要被局部变量表中直接或间接引用的对象都不会被回收
  • 操作数栈
    • 方法执行过程中根据字节码指令，往操作数栈中写入数据或提取数据，即入栈/出栈
    • 保存计算过程的中间结果，同时作为计算过程中变量临时的存储空间
    • 如果被调用的方法带有返回值，其返回值会被压入当前栈帧的操作数栈中
  • 动态链接
    • 每一个栈帧内部都包含一个指向运行时常量池中该栈帧所属方法的引用，为了支持当前方法的代码能够实现动态链接
    • 源文件被编译到字节码文件中时，所有的变量和方法引用都作为符号引用保存在class文件的常量池里，动态链接的作用就是为了将这些符号引用转换为调用方法的直接引用
    • **为什么需要运行时常量池？**不可能在栈帧中每次都存储对象来调用，通过指向常量池中的对象，减少内存使用
    • 面向对象编程中，频繁用到动态分派。因此为了提高性能，JVM在类的方法区建立了一个虚方法表。使用索引来代替查找
  • 方法返回地址
    • PC寄存器存储的地址
    • 异常退出就不保存方法返回地址信息
  • 一些附加信息

本地方法栈

本地方法栈就是用于管理本地方法的调用

本地方法

使用native关键字修饰的方法，就是一个Java调用非Java代码的接口

使用的原因：一些层次的任务用Java实现不容易，或者对程序的效率很在意

  • 与Java环境外交互
  • 与操作系统的交互
  • Sun’s Java

使用的很少了现在

某个线程调用一个本地方法时，就进入了不受虚拟机限制的世界，它和虚拟机拥有相同的权限

  • 可以通过本地方法接口来访问虚拟机内部的运行时数据区
  • 甚至可以直接使用本地处理器中的寄存器
  • 直接从本地内存堆中分配任意数量内存

并不是所有JVM都实现了本地方法

Hotspot JVM中直接将本地方法栈和虚拟机栈合二为一

堆

一个JVM示例(也就是一个进程)只存在一个堆内存

堆区在JVM启动的时候就被创建了，空间大小也就确定了

  • 堆的大小可以调节

堆的物理上不连续，逻辑上应该被视为连续

堆上实际上还可以划分线程私有的缓冲区(TLAB)

所有的对象实例以及数组都应当在运行时分配在堆上(课上老师说是几乎，因为逃逸分析，栈上分配等)

方法结束后，堆中的对象不会马上移除，在垃圾回收启动的时候才会被移除

  • Java7 逻辑上新生区+养老区+永久区
  • Java8 逻辑上新生区+养老区+元空间

JVM参数

-XX:+PrintFlagsInitial查看所有的参数的默认初始值

-XX:+PrintFlagsFinal查看所有的参数的最终值(可能会存在修改，不再是初始值)

-Xms设置堆空间的初始大小 -Xmx设置堆空间的最大内存大小

-Xmn:设置新生代的空间大小(一般不设置)

默认堆空间大小：初始-物理内存/64 最大内存大小-物理内存/4

-XX:NewRatio=ratio 默认为2 老年代:年轻代=2：1

-XX:SurvivorRatio=ratio 设置新生代中Eden和S0/S1空间的比例

-XX:MaxTenuringThreshold设置新生代垃圾的最大年龄

-XX:+PrintGCDetails输出详细的GC处理日志

-XX:HandlePromotionFailure（JDK7之后失效了，不用学）

  • Minor GC之前，虚拟机会检查老年代最大可用的连续空间是否大于新生代所有对象的总空间
    • 如果大于，则此次Minor GC是安全的
    • 如果小于，则虚拟机会查看-XX:HandlePromotionFailure设置值是否允许担保失败
      • 如果HandlePromotionFailure=true，那么会继续检查老年代最大可用连续空间是否大于历次晋升到老年代的对象的平均大小
        • 如果大于，则尝试进行一次Minor GC，但这次Minor GC依然有风险
        • 如果小于，则改为一次Full GC
      • 如果HandlePromotionFailure=false，则改为一次Full GC

-XX:UseAdaptiveSizePolicy 关闭自适应的内存分配策略

  • 年轻代

    • Eden

    • Survivor0(和Survivor1比谁空谁是to区，放对象的是from)

    • Survivor1

      HotSpot Eden空间和另外两个Survivor空间默认所占的比例是8：1：1

      几乎所有的Java对象都是在Eden区被new出来的

      对象放到Eden里满了之后，触发YGC，将不需要回收的对象存到to区中，然后对from区中的对象进行判断，还不需要回收的，也全部放到to区中

      如果对象的age达到15(默认阈值)后，Promotion到老年区。设置参数-XX:MaxTenuringThreshold=

      幸存者区被动触发YGC，只有Eden园区满了才会触发YGC，这时候会将幸存者区中的垃圾一并回收

  • 老年代

    • 如果幸存者区中相同年龄的所有对象大小总和大于Survivor空间的一半，年龄大于或等于该年龄的对象可以直接进入老年代，无需等到年龄阈值

GC按照回收区域分为：

  • 部分收集(Partial GC)
    • 新生代收集(Minor GC/YGC)新生代的垃圾收集
    • 老年代收集(Major GC/Old GC)只是老年代的垃圾收集
      • 目前只有CMS GC会有单独收集老年代的行为
      • 注意，很多时候Major GC会和Full GC混淆使用，需要具体分辨是老年代回收还是整堆回收
      • 老年代空间不足时，会先尝试触发Minor GC，如果空间还不足则触发Major GC
    • 混合收集(Mixed GC):收集整个新生代以及部分老年代的垃圾收集
      • 目前只有G1 GC会有这种行为
  • 整堆收集(Full GC)
    • 收集整个Java堆和方法区的垃圾收集

TLAB(Thread Local Allocation Buffer)

堆区是线程共享区域，任何线程都能访问堆区中的共享数据

由于对象实例创建在JVM中非常频繁，因此在并发环境下从堆区中划分内存空间是线程不安全的

为避免多个线程操作同一地址，需要使用加锁等机制，进而影响分配速度

在Eden区分配，JVM为每个线程分配了一个私有缓存区域

JVM将TLAB作为内存分配的首选，TLAB非常小，仅占有Eden空间的1%，对象在TLAB中分配内存失败，JVM就会尝试通过使用加锁机制确保数据操作的原子性

堆是分配对象的唯一选择吗？

JDK7开始逃逸分析默认开启

逃逸分析，分析出新的对象的引用使用范围决定是否将对象分配到堆上

  • 没有发生逃逸的对象就可以分配到栈上，随着方法执行结束被移除

垃圾回收

常量池中废弃常量和不再使用的类型

常量池的回收策略很明确，常量只要没有被引用，就可以被回收

判断类不再被使用，需要满足下面三个条件(条件非常苛刻，但有时是必要的)

  • 所有实例以及任何派生子类的示例都被回收
  • 加载类的加载器已经被回收（很难达成）
  • java.lang.Class对象没有被引用

对象实例化

创建方式

  • new(有变种，比如类的静态方法(单例),XXXBuilder,XXXFactory)
  • Class的newInstance()，反射的方式，只能调用空参的构造器，权限必须是public
  • Constructor的newInstance(Xxx)，反射的方式，可以调用空参、带参构造器，权限没有要求
  • 使用clone()，不调用任何构造器，当前类需要实现Cloneable接口，实现clone()
  • 反序列化
  • 第三方库Objenesls

创建步骤

  • 对应的类是否加载、链接、初始化，没加载的话就双亲委派机制加载类
  • 分配内存
    • 内存规整(指针碰撞，指针从已占用的空间结尾偏移到新创建的对象空间之后)
    • 内存不规整(维护空闲列表，记录那些内存块可用，找到足够大的空间分配实例)
    • 内存是否规整取决于使用的垃圾收集器
  • 处理并发问题
    • CAS
    • TLAB
  • 初始化分配到的空间(属性初始化，赋默认值)
  • 设置对象的对象头(所属的类、HashCode、对象的GC信息、锁信息等数据)
  • 执行init方法

对象内存布局

  • 对象头
    • 运行时元数据
      • HashCode 对象引用
      • GC分代年龄
      • 锁状态标志
      • 线程持有的锁
      • 偏向线程ID
      • 偏向时间戳
    • 类型指针
      • 指向对象所属的类型
    • 如果是数组，还要记录数组长度
  • 实例数据
    • 先放父类，再放子类
    • 相同宽度字段总是分配在一起
    • CompactFields，子类的窄变量可以插入到父类变量的间隙
  • 对齐填充
    • 没啥用，占位符

对象访问方式

  • 句柄访问(实际上就是栈帧中的对象引用指向堆的句柄池中的对象实例指针，和对象类型数据指针是连续的，这两个指针再分别指向实例数据和方法区中的类型数据)
    • 好处：栈空间的对象引用地址很稳定
    • 坏处：效率低
  • 直接指针(HotSpot) 直接指向堆中的对象实例数据，示例数据中保存了对象类型数据指针

执行引擎

什么是解释器，什么是JIT编译器

解释器：当Java虚拟机启动时会根据预定义的规范对字节码采用逐行解释的方式执行，将每条字节码文件中的内容“翻译”为对应平台的本地机器指令执行

JIT：虚拟机将源代码直接编译成本地机器平台相关的机器语言，并缓存

解释器和JIT编译器是怎么并存的

解释器

  • 响应速度快

JIT编译器

  • 执行效率高

虚拟机启动，解释器首先发挥作用，不必等待全部编译完成后再执行，省去许多不必要的编译时间。随着运行时间推移，JIT编译器发挥作用，根据热点探测功能，将有价值的字节码编译为本地机器指令，换取更高的程序执行效率

JIT编译热点代码探测

方法调用计数器-热度衰减，一定事件后就会衰减一半

-Xint：完全采用解释器

-Xcomp：完全采用即时编译器模式，如果出现问题，解释器会介入执行

-Xmixed：混合执行

垃圾回收

垃圾是运行程序中没有任何指针指向的对象

标记阶段算法

  • 引用计数算法

对每个对象保留一个整形的计数器，记录被对象引用的情况

优点：实现简单，判定效率高

缺点：

1.存储空间开销

2.赋值更新计数器，时间开销

3.无法处理循环引用(致命缺陷，Java不用这个) 会造成内存泄漏

  • 可达性分析算法（根搜索算法、跟踪性垃圾收集）

从上至下搜索被根对象集合所连接的目标对象是否可达

搜索走过的路径称为引用链

GC Roots包括以下几类元素

  • 虚拟机栈中引用的对象
  • 本地方法栈中引用的对象
  • 方法区类静态属性引用的对象
  • 方法区中常量引用的对象
  • 所有被同步锁synchronized持有的对象
  • Java虚拟机内部的引用（系统类加载器）
  • 反应Java虚拟机内部情况的JMXBean、JVMTI中注册的回调、本地代码缓存等

还可以有其他对象临时加入GC Roots，比如分代收集和局部回收

分析工作必须在能保障一致性的快照中进行，这也是必须STW的一个重要原因，即使是号称不会停顿的CMS中，枚举根节点也是必须要停顿的

对象的finalization机制

允许开发人员允许对象被销毁之前自定义处理逻辑

不要主动调用，原因：

  • 可能导致对象复活
  • 执行时间没有保障
  • 糟糕的finalize()严重影响GC性能

虚拟机的对象可能的三种状态：

  • 可触及的
  • 可复活的
  • 不可触及的

finalize()是对象逃脱死亡的最后机会，一个对象的这个方法只会被调用一次

垃圾清除阶段算法

  • 标记-清除算法

    • 标记

      从根节点开始遍历，标记所有被引用的对象

    • 清除

      对堆内存从头到尾线性遍历，如果没有被标记，就回收

缺点：

1.效率低

2.GC时停止整个应用程序，影响用户体验

3.清理出来的内存不是连续的

这里的清楚不是真的置空，而是把需要清除的对象地址保存在空闲的地址列表里。下次有新对象时，判断垃圾的位置空间是否够，如果够就存放。

  • 复制算法(适合新生代)

将内存空间分为两块，每次只使用其中一块，垃圾回收时将正在使用的内存中的存活对象复制到未被使用的内存块中，之后清楚正在使用的内存块中所有对象，然后交换内存的角色(类似于from区和to区的样子)

优点

1.运行高效

2.没有碎片

缺点

1.需要2倍的内存空间

2.对于G1这种分拆为大量区域的GC，复制意味着需要维护region之间的对象引用

  • 标记-压缩算法(标记整理算法)(适合老年代)

将标记的存活对象压缩到内存的一端，按顺序排放，之后清理边界外所有的空间

优点

1.内存区域连续

2.不用需要两倍的内存空间

缺点

1.效率上低于复制算法

2.移动对象时，还需要调整引用它的地址

3.移动过程中STW

分代收集算法

  • 年轻代
    • 区域小、对象生命周期短、存活率低、回收频繁
    • 复制算法，效率只和存活对象大小有关，内存利用率低的问题也通过两个幸存者区得到缓解
  • 老年代
    • 区域大，对象生命周期长，存活率高，回收不及年轻代频繁
    • Mark阶段开销和存活对象数量成正比
    • Sweep阶段的开销与所管理区域的大小成正相关
    • Compact阶段的开销和存活对象的数据成正比

增量收集算法

每次垃圾收集线程只收集一小块内存，接着切换到用户线程，依次反复直到收集完成

基础仍是传统的标记-清除和复制算法。

**缺点：**线程切换和上下文切换的消耗，会使得垃圾回收总成本上升，系统吞吐量下降

分区算法

为了更好地控制STW的时间，将一块大的内存区域分割为多个小块，根据目标的停顿时间，每次回收若干个小空间而不是整个堆空间，从而减少GC的停顿

内存泄露

只有对象不会被程序用到了，但是GC又不能回收他们，才叫内存泄漏

疏忽导致对象的生命周期变得很长甚至导致OOM，也可以叫宽泛上的内存泄漏

并不会立即引起程序崩溃，但是发生内存泄漏，可用内存就会逐步被蚕食，直至耗尽所有内存出现OOM

例子

  • 单例模式

    如果持有对外部的对象引用，那么这个外部对象不可被回收，导致内存泄露

  • 一些提供close的资源未关闭

Java中几种不同的引用

  • 强引用

    new的对象，永远不回收

  • 软引用

    将要内存溢出之前，会把这些对象列入范围内进行二次回收，如果这次回收后还没有足够内存，才会抛出OOM

    Object obj=new Object();

    SoftReference<Object> sf=new SoftReference<Object>(obj);

    obj=null;

  • 弱引用

    只要垃圾收集器工作，无论空间是否足够，都会回收弱引用关联的对象

    WeakReference<Object> wr=new WeakReference<Object>(obj);

  • 虚引用

    获取不到对象，唯一目的就是让这个对象被收集器回收时收到一个系统通知

    Object obj=new Object();

    ReferenceQueue phantomQueue=new ReferenceQueue();

    PhantomReference<Object> pf=new PhantomReference<Object>(obj,phantomQueue);

    obj=null;
